# Wishlist Bot

[![CI](https://github.com/VovaKyrylenko/wishlist-bot/actions/workflows/ci.yml/badge.svg)](https://github.com/VovaKyrylenko/wishlist-bot/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

Telegram-бот для списків бажань: зібрати, поділитися посиланням, і щоб друзі не подарували одне й те саме. Жодної реєстрації, окремого сайту чи складного інтерфейсу — усе відбувається прямо в переписці.

Взаємодія побудована за [docs/UX-REDESIGN.md](docs/UX-REDESIGN.md) і тримається на трьох правилах:

1. **Один якір.** Унизу — рівно одна кнопка `🏠 Головна`. Вона працює звідусіль, включно з серединою будь-якої дії, де означає «скасувати й повернутись».
2. **Один живий екран.** Актуальний стан завжди внизу чату. Тап по кнопці з повідомлення тижневої давнини не лається «кнопка застаріла», а тихо малює свіжий екран цієї сутності.
3. **Ввід завжди валідний.** Посилання, фото чи назва, надіслані будь-де й будь-коли, — це «додати подарунок». Бот ніколи не мовчить.

## Стек

- **Node.js + TypeScript** (без фреймворку)
- **[grammY](https://grammy.dev)** — Telegram Bot API. Без `@grammyjs/conversations`: покрокові діалоги замінені станом `pendingAction` на користувачі (див. «Нотатки з архітектури»)
- **Prisma 7 + Neon Postgres** — дані, чернетки й стан живого екрана
- **Vercel** — деплой вебхука як serverless-функції (`api/webhook.ts`)

  drafts.ts              Незбережені подарунки — превʼю-картка й «Продовжити?»

  entry.ts               /start і deep links, розумний ввід (посилання/фото/текст)
  home.ts                🏠 Головна, онбординг, списки друзів, завершені, «Про мене», дайджест
  lists.ts               Мій список, поширення, «Про список», співавтори, завершення, видалення

  promises.ts            «🎗 Я дарую»: куплено / відпустити

## Налаштування

### 1. Створіть бота у BotFather

У Telegram напишіть [@BotFather](https://t.me/BotFather) → `/newbot`, дайте ім'я та юзернейм. Скопіюйте виданий токен.

### 2. Змінні середовища

Скопіюйте `.env.example` → `.env` (для локальної розробки) і заповніть:

```
BOT_TOKEN=       # токен з BotFather
WEBHOOK_SECRET=  # будь-який випадковий рядок — захищає /api/webhook від чужих запитів
WEBHOOK_URL=     # https://<ваш-проєкт>.vercel.app/api/webhook (потрібен лише для set-webhook)
DATABASE_URL=            # Neon, пул-з'єднання
DATABASE_URL_UNPOOLED=   # Neon, пряме з'єднання (для міграцій)
AI_GATEWAY_API_KEY=      # ключ Vercel AI Gateway — назви подарунків із посилань
```

Без `AI_GATEWAY_API_KEY` бот працює: назву бере з розмітки сторінки, а там, де розмітка дає сміття («Головна», назва магазину, підпис з Instagram), просить написати назву самому. Ключ створюється в розділі AI Gateway на Vercel; модель і ендпоінт можна перевизначити через `AI_GIFT_NAME_MODEL` та `AI_GATEWAY_URL` (ADR 0006).

`DATABASE_URL` / `DATABASE_URL_UNPOOLED` уже підтягнуті автоматично, якщо проєкт залінкований з Vercel і підключена інтеграція Neon (`vercel env pull .env.local`, потім скопіюйте в `.env`).

### 3. Встановлення та база даних

```bash
npm install                # також запускає prisma generate (postinstall)
npm run prisma:migrate     # застосувати схему до Neon (лише при першому запуску / зміні schema.prisma)
```

### 4. Локальний запуск (long polling, без деплою)

```bash
npm run dev
```

Це найпростіший спосіб перевірити бота — жодного публічного URL не потрібно. Скрипт сам знімає вебхук перед стартом polling.

### 5. Продакшн-деплой на Vercel (вебхук)

```bash
vercel deploy --prod
```

Переконайтесь, що `BOT_TOKEN`, `WEBHOOK_SECRET`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED` додані в Vercel (Project Settings → Environment Variables — Neon-змінні вже мають бути там після підключення інтеграції).

Після деплою зареєструйте вебхук (один раз, або щоразу як змінюється домен):

```bash
WEBHOOK_URL=https://<ваш-проєкт>.vercel.app/api/webhook npm run webhook:set
```

Щоб повернутись до локального polling пізніше — `npm run webhook:delete`.

## Основний сценарій

1. `/start` → один екран, одне речення, одна кнопка. Назву списку закривають пресети («🎂 День народження») в один тап.
2. Далі власник просто **надсилає** посилання, фото або назву — з екрана списку чи звідки завгодно. З посилання бот витягує назву, фото й ціну; фото стає карткою; підпис — назвою.
3. Виходить **превʼю-картка, яку можна правити до збереження**: назва, ціна, фото, кількість, «наскільки хочу». Нічого не записано, доки не натиснуто «✅ Додати».
4. Після третього подарунка бот сам виводить «📤 Поділитися» першою кнопкою й показує превʼю того, що побачить друг, разом із посиланням `https://t.me/<bot>?start=list_<slug>`.
5. Гість відкриває посилання й **одразу бачить вітрину** — без реєстрації й проміжних екранів. Вільні подарунки вгорі, зайняті позначені словами «✅ вже дарують».
6. Тап по подарунку → «🎁 Я подарую це» → готово. Жодних кількостей, контактів і підтверджень; поруч одразу «↩️ Передумав».
7. Власник отримує сповіщення, яке **не ламає сюрприз**: у режимі сюрпризу — лише факт, без назви подарунка й імені.
8. Свої обіцянки гість знаходить у «🎗 Я дарую», згруповані за списками, і позначає «✅ Я вже купив» за два тапи.

## Нотатки з архітектури

- **Живий екран.** Тап, що прийшов *із* поточного екрана, редагує його на місці; тап із будь-чого старішого малює свіжий екран унизу чату. Указівник живого повідомлення лежить у `User.screenMessageId`, логіка — у [src/lib/screen.ts](src/lib/screen.ts). Саме це прибирає з продукту фразу «ця кнопка застаріла»: стара кнопка тепер не помилка, а ярлик назад у продукт. Довгі списки не розсилаються по повідомленню на пункт — вони нумеруються в тексті, а кнопки це компактні індекси `1 2 3` плюс пагінація.
- **Без conversations.** Діалоги були головною проблемою старого бота: conversation володіє наступним апдейтом, тож будь-який тап посеред питання отримував «Спершу заверши цей крок 🙂». Тепер питання — це просто запис `pendingAction` на користувачі ([src/lib/pending.ts](src/lib/pending.ts)): наступне звичайне повідомлення стає відповіддю, всі кнопки працюють як зазвичай, а **будь-який тап знімає покинуте питання** (middleware в [src/bot.ts](src/bot.ts)) — інакше текст, написаний через годину, вважався б відповіддю на давно забуте питання.
- **Чернетки.** Подарунок збирається в `Draft` і стає `WishlistItem` лише на «✅ Додати» ([src/lib/drafts.ts](src/lib/drafts.ts)). Звідси і повністю редаговане превʼю, і те, що піти на півдорозі нічого не коштує: наступний контакт пропонує «Продовжити?».
- **Контракт сюрпризу.** `privacyMode = SURPRISE` (дефолт) означає, що власник не бачить ні хто, ні що, ні скільки — **лічильники ховаються теж**, інакше «заброньовано 1 з 1» видає сюрприз не гірше за ім'я. «Пульс» списку показує число лише від 4 подарунків, нижче — беззмістовне «список живий». Уся приватна гілка сповіщень живе в [src/lib/notify.ts](src/lib/notify.ts), а не по місцях виклику.
- **Телефон більше не питається.** Це був найдорожчий крок воронки в найкрихкішому місці — перший контакт гостя. Роль антиспаму виконує сам Telegram-акаунт. Колонка `contactPhone` лишилась тільки щоб ті, у кого номер уже збережений, могли його видалити в «Про мене».
- **PURCHASED тримає слот.** Доступність рахується по `ACTIVE + PURCHASED` (`holdingReservations` у [src/lib/availability.ts](src/lib/availability.ts)). Якщо рахувати лише `ACTIVE`, то гість, який чесно тиснув «✅ Я вже купив», повертав подарунок у список як вільний — і другий гість купував те саме.
- **М'яке видалення з undo.** `WishlistItem.status = DELETED` замість `delete`: каскад стирав і обіцянки, тож гість втрачав запис про вже куплений подарунок. `deletedAt` дає п'ять хвилин на «↩️ Повернути», а `Reservation.autoCancelledAt` позначає рівно ті обіцянки, які зламало це видалення, щоб повернути саме їх.
- **Підтвердження чи undo — за одним правилом.** Питаємо лише там, де дія незворотна або зачіпає інших: видалення списку (два кроки, без undo, і про це сказано прямо), відпустити подарунок, вимкнути сюрприз. Решта — миттєва дія плюс «↩️ Повернути» в тому самому екрані, де вона не може «згаснути» за дві секунди.
- **Співавтори — через одноразове інвайт-посилання**, а не за юзернеймом: `getChat("@username")` не резолвить звичайних користувачів. Запрошений спершу бачить екран «{Ім'я} запрошує тебе вести список «{Назва}»» і вирішує сам. На екрані списку співавтор бачить рядок про свою роль замість кнопки, яка йому все одно відмовить.
- **Ідемпотентність вебхука.** Telegram передоставляє апдейт, якщо відповідь забарилась (а скрапінг сторінки має вісім секунд), і ретрай додавав товар чи бронював подарунок удруге. `ProcessedUpdate` «застовплює» `update_id` до обробки.
- **Обрізання тексту знає про HTML.** `truncateHtml` ніколи не ріже всередині тега чи сутності й дозакриває відкриті теги — інакше довгий коментар давав `can't parse entities`, і екран не з'являвся взагалі.
- **Скрапер посилань ходить лише в публічний інтернет**: заборонені loopback, link-local (метадані хмари), приватні діапазони, редіректи перевіряються на кожному хопі, тіло відповіді обмежене 2 МБ.

## Cron

`/api/cron` ([api/cron.ts](api/cron.ts)) запускається щогодини (`vercel.json`, `0 * * * *`) і робить чотири речі:

1. **Нагадування за `eventDate`** — за 3 дні до події гостям (ті, хто стежить + ті, хто просто відкривав список) і власнику. До цього дата збиралась і показувалась, але ні на що не впливала. Повторів не буде: `Wishlist.reminderSentAt` ставиться після розсилки й скидається лише при зміні дати.
2. **Дайджест тим, хто стежить** — одне повідомлення на список замість одного на кожен доданий подарунок. Щогодинний ритм означає, що вечір заповнення списку складеться в одне-два повідомлення, а не двадцять.
3. **Чистка `ProcessedUpdate`** старших за добу.
4. **Чистка чернеток і покинутих питань** старших за добу. Термін і так перевіряється при читанні — це лише щоб рядки не накопичувались.

Погодинний розклад потребує плану Pro — на Hobby Vercel Cron дозволяє один запуск на добу, тоді ставте `0 9 * * *`.

Локально можна смикнути вручну: `curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron`.

## Перевірка розбору посилань

```bash
npm run verify:scrape
```

[scripts/scrape/](scripts/scrape/) перевіряє, що саме бот витягне з чужої сторінки: JSON-LD, `@graph` з `AggregateOffer`, мікродані, самий OpenGraph, сторінку зовсім без розмітки (зі старою ціною та доставкою поруч), windows-1251, поламаний JSON-LD. Окремо — назви (декоративні префікси, SEO-хвости, дефіс у моделі товару) і валюти (`₴ $ € £ zł`, ISO-коди, «грн»). Бази даних не потребує й у мережу не ходить.

## Перевірка флоу

```bash
DATABASE_URL=<staging> npm run verify:flows
```

[scripts/flows/](scripts/flows/) проганяє бота синтетичними Telegram-апдейтами: онбординг, розумний ввід, чернетка-превʼю, гостьова обіцянка, undo, співавтори, завершення й видалення списку — і перевіряє не лише «не впало», а й самі правила редизайну: що сповіщення власнику не видає сюрприз, що стара кнопка не отримує «застаріла», що покинуте питання знімається.

Кожен вихідний виклик Telegram перехоплюється, тож нікому нічого не надсилається. **База при цьому справжня, і між наборами вона витирається** — тому харнес відмовляється стартувати, якщо в імені бази немає `staging`:

```
Error: refusing to run against database "neondb" — point DATABASE_URL at a staging database
```

Ізолювати запуск через `search_path` або `?schema=` **не вийде**: Prisma підставляє `public.` у кожен запит, тож міграції поїдуть у вказану схему, а сам клієнт усе одно піде в `public`. Єдина справжня межа — окрема база:

```bash
psql "$DATABASE_URL_UNPOOLED" -c 'CREATE DATABASE wishlist_staging;'
DATABASE_URL_UNPOOLED="${DATABASE_URL_UNPOOLED/\/neondb?//wishlist_staging?}" npx prisma migrate deploy
```
