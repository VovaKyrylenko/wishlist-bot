# Contributing

Дякуємо за інтерес до проєкту! Тут все максимально просто — і процес контриб'юції теж такий.

## Швидкий старт

1. Форкніть репозиторій і склонуйте свій форк.
2. Потрібні Node (24; підійде й 22.12+, див. `engines` у `package.json` та `mise.toml`) і pnpm: версію pnpm береться з `packageManager`, тож достатньо будь-якого pnpm 10+ (`npm i -g pnpm`). Далі `pnpm install` (заодно виконає `prisma generate`). Лише pnpm: звичайний `npm install` у цьому каталозі падає. Під час встановлення pnpm друкує «Ignored build scripts: prisma»: це очікувано й безпечно.
3. Створіть власного тестового бота через [@BotFather](https://t.me/BotFather) і свою Neon/Postgres базу — не використовуйте продакшн-дані.
4. Скопіюйте `.env.example` → `.env`, заповніть `BOT_TOKEN`, `DATABASE_URL`, `DATABASE_URL_UNPOOLED`.
5. `pnpm run prisma:migrate`, потім `pnpm run dev` — бот піднімається через long polling, деплой не потрібен.

Детальніше про архітектуру — у [README.md](README.md).

## Перш ніж відкривати PR

- `pnpm run typecheck`, `pnpm run lint` і `pnpm test` мають проходити без помилок.
- Змінили `src/features/`, `api/` чи `prisma/` — запустіть ще й `pnpm run verify:flows` (див. «Тести» нижче).
- Перевірте зміну вручну через `pnpm run dev`: бот невеликий, ручна перевірка сценарію швидша й надійніша за будь-які тести з моками.
- Якщо змінили `prisma/schema.prisma` — додайте міграцію (`pnpm run prisma:migrate --name опис_зміни`) і закомітьте `prisma/migrations/`.

## Тести

`pnpm test` запускає юніт-тести разом з порогами покриття (`vitest.config.ts`). Йому не потрібні ні база, ні токен бота, він працює менше секунди й точно так само виконується в CI та перед `git push`. Для швидкого циклу: `pnpm run test:watch` або `pnpm exec vitest run <файл>` (без порогів покриття).

Що перевіряють юніт-тести: доступність подарунка (щоб ніхто не подарував одне й те саме двічі), правила доступу до списку, формат посилань, розбір сторінок і дати. Пороги стоять лише на файлах, регресія в яких боляче вдарила б по людях, і трохи нижче за виміряне, а не «100%».

Чого вони **не** перевіряють: усе, що працює з базою, тобто обробники в `src/features/` (зокрема, що дія «лише для власника» справді перевіряє власника) та `api/`. Це перевіряє лише `pnpm run verify:flows`: він проганяє бота синтетичними оновленнями Telegram й стирає таблиці, тому відмовляється працювати, якщо в назві бази немає слова «staging». У CI цього немає (немає секрету зі staging-базою), тож запускайте його самі перед тим, як зливати зміни в `src/features/`, `api/` чи `prisma/`. Воркфлоу `flows.yml` можна запустити вручну, коли власник створить у налаштуваннях репозиторію середовище (Environment) `staging`, дозволене лише для гілки `main`, і збереже в ньому секрет `STAGING_DATABASE_URL`.

Змінили логіку, яку вже покривають тести, і вони стали червоними: виправляйте код або тест, що помилився, але не послабляйте перевірку, щоб вона пройшла.

## Стиль коду

- TypeScript strict, без `any`, де можна цього уникнути.
- Не додавайте абстракції «про запас» — прямий код для конкретної задачі кращий за передчасну гнучкість.
- Тексти для користувача — українською (це продукт для українськомовної аудиторії); коментарі в коді, назви змінних і комміти — англійською.
- Усі тексти бота живуть у `src/text.ts` — не додавайте текстові літерали в `src/features/*`. Тон голосу, словник і візуальний стиль (емодзі) описані в [CLAUDE.md](CLAUDE.md) та [.claude/rules/voice.md](.claude/rules/voice.md) — дотримуйтесь їх, редагуючи чи додаючи тексти.
- Коментарі лише там, де важлива причина рішення (WHY), а не опис того, що й так видно з коду.

## Що варто, а що не варто пропонувати

Головна цінність бота — короткий і зрозумілий шлях "створив список → надіслав посилання → люди забронювали подарунки". PR, які додають функціональність поза цим (внутрішні соцмережі, оплата всередині бота, складні ролі доступу тощо), швидше за все буде відхилено — не тому що ідея погана, а тому що вона суперечить філософії проєкту. Якщо не впевнені — відкрийте issue з описом ідеї перед тим, як писати код.

## Повідомлення про баги та ідеї

Використовуйте шаблони issue в GitHub — вони підказують, яку інформацію варто додати.
